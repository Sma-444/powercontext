# CAP 定理：到底在限制什么

## 一句话版本

CAP 说的是：当网络分区真实发生、系统必须继续对外服务时，你只能在「一致性」和「可用性」之间选一个。
它不是「三选二」的静态配置，而是**分区期间的取舍**。

## 三个字母的准确定义

- **C（Consistency）**：这里的 C 是**线性一致性**，不是「最终一致」「弱一致」这种宽泛说法。
  对同一个对象，读操作必须能看到此前已经完成的写，且所有节点看到同一个顺序。
- **A（Availability）**：每个到达**非故障节点**的请求，都必须在**有限时间**内返回**非错误**响应。
  注意「有限时间」和「非错误」是两个硬条件，超时和 5xx 都算不满足 A。
- **P（Partition tolerance）**：网络分区指节点之间的消息可能被丢弃或延迟任意长时间。
  分区不是「会不会发生」，而是「什么时候发生」。

## 为什么 CA 在分布式系统里不成立

只要系统跨机器部署，网络分区就一定会出现。分区发生时，如果坚持 C，就必须拒绝一部分请求
（牺牲 A）；如果坚持 A，就可能读到旧数据（牺牲 C）。所以真实系统要么是 CP，要么是 AP，
所谓 CA 只在单机或「假设网络永不分分区」的模型里成立。

## 常见误解

1. **「CAP 让我选两个」**：准确说法是「P 必须保留，然后在 C 与 A 之间做选择」。
   放弃 P 的分布式系统在工程上不存在。
2. **「选了 AP 就没有一致性」**：AP 系统放弃的是分区期间的强一致，通常仍提供**最终一致性**，
   并通过读修复、反熵等机制收敛。
3. **「CAP 能指导所有设计」**：CAP 只讨论分区期间。延迟（latency）与分区无关，
   所以后来才有 PACELC：分区时在 C/A 之间选，平时在延迟 L 与一致性 C 之间选。

## BASE：对 AP 的工程化表述

- **Basically Available**：允许降级、允许部分失败，但整体仍可用。
- **Soft state**：允许中间状态存在，不要求任何时刻都是终态。
- **Eventually consistent**：在没有新写入的前提下，副本最终会收敛到同一值。

BASE 不是 CAP 的替代理论，而是「选择 AP 之后，工程上怎么把一致性补回来」的一组手段：
读修复、提示移交（hinted handoff）、反熵（Merkle tree 比对）、业务补偿。

## 工程取舍对照

| 场景 | 倾向 | 理由 |
| --- | --- | --- |
| 支付扣款、库存扣减 | CP | 宁可失败也不能超卖或重复扣款 |
| 商品详情、点赞数、购物车 | AP | 短时间展示旧值可以接受，可用性优先 |
| 分布式锁、主节点选举 | CP | 依赖多数派确认，避免脑裂 |
| 会话、Feeds 流 | AP + 读己之写 | 用会话粘滞或版本号补用户体验 |

## 和 Raft / Dynamo 的关系

- **Raft** 是典型的 CP 路径：写入必须获得多数派确认，分区时少数派一侧无法提交，只能拒绝写。
- **Dynamo** 是典型的 AP 路径：用一致性哈希分片、向量时钟记录因果、`(N,R,W)` 调节读写票数，
  允许临时不一致，再用反熵收敛。
- **两阶段提交（2PC）** 常被误认为 CAP 里的 C，其实它保证的是**原子提交**，
  而且在协调者失败时会阻塞，既牺牲可用性也没解决分区下的共识问题。
