# 技术结合说明：seekdb 与 PowerContext 各自承担什么

> 评审关注点：两项技术是否**在功能里真的起作用**，以及能否拿记录核对。
> 本文按「做了什么 → 代码在哪 → 怎么核对」三段写，避免自述式描述。

---

## 一、seekdb：不是「装了个数据库」，而是检索的唯一来源

### 1.1 表与索引

| 对象 | 作用 |
| --- | --- |
| `duban_documents` | 一篇资料一行：`doc_id`、`revision`（内容 sha256 前 12 位）、页数、片段数 |
| `duban_chunks` | 一个片段一行：页号 `page` / 行号区间、正文 `body`、检索投影 `searchable` |
| `duban_chunks_fts` | `CREATE FULLTEXT INDEX … (searchable) WITH PARSER NGRAM` |

**为什么用 NGRAM 解析器**：seekdb 自带的 `NGRAM` 解析器对中文直接按 2 字切分，
不需要外部分词服务，也不需要把中文预切成空格分隔的词（后者用 `SPACE` 解析器实测对中文无效，
见 `.qoderwork` 里的探针记录）。一篇中文笔记、一篇英文论文可以放在同一张表里检索。

**为什么 `searchable` 要拼上标题与小节名**：用户经常用「选举」「反熵」这种
只出现在小标题里的词提问；只索引正文会漏召回。

### 1.2 检索语句

候选由数据库算分，Python 只做重排：

```sql
SELECT chunk_id, doc_id, doc_title, path, page, anchor, body,
       MATCH(searchable) AGAINST (:query) AS score
FROM duban_chunks
WHERE MATCH(searchable) AGAINST (:query)
ORDER BY score DESC, chunk_id
LIMIT :limit
```

一次提问会发 2–4 条这样的语句（原问题、内容词、技术词），合并后重排。
每条语句、参数、返回行数、耗时都写进 `records/db/queries.jsonl`。

### 1.3 结构化过滤与回查

- 按文档过滤（`doc_id IN (…)`）用于「只在这篇里找」；
- `page_text(doc_id, page)` 把引用 `path#p12` 还原成原文，供界面弹层显示；
- `chunks_of(doc_id)` 供评测核对引用是否真实存在。

### 1.4 代码位置

| 文件 | 内容 |
| --- | --- |
| `duban/store.py` | 建表、索引、增量同步、`search` / `page_text` / `chunks_of` / SQL 日志 |
| `duban/retrieve.py` | 多路召回与重排 |

### 1.5 怎么核对

```bash
python -m duban ask "Dynamo 用哪种数据结构做反熵？" > /dev/null
tail -5 records/db/queries.jsonl | python -m json.tool --json-lines
```

能看到 `operation=search`、`sql` 里含 `MATCH … AGAINST`、`rows` 与 `elapsed_ms`。

## 二、PowerContext：记忆改变了下一次回答

### 2.1 四类 artifact

| kind | 内容 | 何时写 | 何时读 |
| --- | --- | --- | --- |
| `duban.profile` | 解释深度（brief/standard/deep）、语言、备注 | 用户切换深度 | 每次作答前决定给几条要点 |
| `duban.weak` | 薄弱点：概念、备注、来源引用 | 用户点「没看懂」/`duban mark` | 提问时匹配 → 触发补正召回 + 记忆提示 |
| `duban.progress` | 每篇读到第几页、百分比 | 用户点「已读到这里」/`duban touch` | 复习清单、检索微调 |
| `duban.turn` | 本次问题、引用列表、涉及文档 | 每次提问 | 下一轮的「上次你问的是…」 |

全部 **append-only**：读取时按 `seq` 取最新，所以进程崩在写到一半也不会毁掉历史。

### 2.2 记忆怎么「被用上」

1. **改变召回**：`retrieve._weak_overlap()` 把问题词项与薄弱点做匹配，命中就额外取一条
   该概念的片段作为「基础补正」，并以 `weak_primer` 的身份参与排序加成。
2. **改变措辞**：`answer.build_answer()` 在 `primer` 存在时插入「先补一条基础说明」区块，
   并在 `memory_note` 里说明「你之前标记过 X 没看懂」。
3. **改变输出长度**：`profile.depth` 决定要点条数（2 / 3 / 4）。
4. **改变复习清单**：`review.build_review()` 把薄弱点、未读完、未开始三类合成待办，
   并给每条挂一个可执行动作（去问 / 继续读）。

### 2.3 代码位置

| 文件 | 内容 |
| --- | --- |
| `duban/memory.py` | artifact 读写、去重计数、`seq` 单调、事件日志 |
| `duban/service.py` | 把 store + memory + retriever 装配成 `ask()` / `state()` |
| `duban/review.py` | 复习清单 |
| `duban/answer.py` | 记忆 → 措辞 |

### 2.4 怎么核对

```bash
python -m duban mark "CAP"
python -m duban ask "CAP 定理到底限制了什么？"    # 应出现「记忆：…」与「先补一条基础说明」
python -m duban state --json | python -m json.tool | head -40
cat records/memory/events.jsonl | tail -3
```

`events.jsonl` 每条都带 `artifact_id`、`seq`、`payload`，可以与
`python -m duban state --json` 里的 `memory.artifact_ids` 对上。

## 三、两者的边界（为什么不是二选一）

| 问题 | 该谁答 | 原因 |
| --- | --- | --- |
| 「哪一页提到 sloppy quorum」 | seekdb | 事实在语料里，需要可回查的位置 |
| 「我上次卡在哪」 | PowerContext | 是用户的经历，不在语料里 |
| 「该先读哪一篇」 | 两者 | 进度来自记忆，资料清单来自库 |
| 「这条结论可信吗」 | seekdb | 引用必须能打开原文 |

这也是为什么项目同时用了两者，而不是只挑一个：
**seekdb 负责「说过什么」，PowerContext 负责「你到哪儿了」。**

---

## 四、没有做的事（避免过度声称）

- 没有接 embedding 模型：`powercontext` 支持挂 embedding，但本项目默认离线，
  向量通道未启用；`duban_chunks` 里也没有向量列。
- 没有做多用户鉴权：作用域隔离靠 `DUBAN_USER`，适合单机自用。
- 没有做 OCR：扫描版 PDF 会被跳过并在导入日志里说明。
